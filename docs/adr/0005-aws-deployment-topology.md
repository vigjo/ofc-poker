# 0005. AWS deployment topology: shared-account, single-cert, no-NAT network

## Status

Accepted

## Context

The plan calls for staging and production on AWS with Route 53/ACM,
CloudFront + S3, an ALB, ECS/Fargate, DynamoDB, IAM least-privilege roles,
and AWS Budgets, deployed via Terraform and GitHub Actions OIDC - all while
staying cost-conscious for a private, low-traffic game (see ADR 0004).

Several sub-decisions needed to be made that the plan leaves open:

## Decisions

### One AWS account, two Terraform state files, not two accounts

Staging and production live in the same AWS account, distinguished by
resource naming (`ofc-staging-*` / `ofc-production-*`) and separate
Terraform state keys (`infra/envs/staging`, `infra/envs/production`), rather
than AWS Organizations + separate accounts. A second account is the
"correct" answer at larger scale (blast-radius isolation, separate billing),
but it roughly doubles setup/operational overhead (two OIDC trusts, two sets
of budgets/alarms, cross-account ECR access) for a project with two
environments and no compliance requirement forcing the split. Revisit if
this becomes a multi-tenant or commercial product.

### No NAT gateway

The Fargate task runs in a public subnet with a public IP, reachable only
from the ALB's security group (see `infra/modules/network`). This saves
~$32/month/environment versus a private-subnet + NAT gateway topology, at
the cost of the task having a public IP (mitigated by the security group -
nothing but the ALB can reach it on any port).

### One ACM certificate for both the ALB and CloudFront

Both `app.<domain>` (CloudFront) and `api.<domain>` (ALB) are covered by a
single ACM certificate with two SANs, issued in `us-east-1`
(`infra/modules/certificate`). This only works because the whole stack is
pinned to `us-east-1`: CloudFront requires its certificate in `us-east-1`
regardless of edge location, and ALB certificates must be in the ALB's own
region - when both are `us-east-1`, one certificate serves both, instead of
provisioning and rotating two.

### A custom domain is required, not optional

Unlike CloudFront (which has a working `*.cloudfront.net` default domain),
an ALB cannot get an ACM certificate without a domain you control, so HTTPS
to the API requires DNS you own with a Route 53 hosted zone already
delegated. There's no "no domain" fallback path in this Terraform - see
`docs/runbooks/aws-bootstrap.md` for what's needed before the first apply.

### JWT keys are generated by Terraform and delivered as env vars, not files

`infra/modules/jwt-keys` generates the RS256 keypair with the `tls`
provider and stores both halves in Secrets Manager. Fargate has no native
"mount a secret as a file" primitive, so the ECS task definition injects
them as environment variables (`OFC_JWT_PRIVATE_KEY_PEM` /
`OFC_JWT_PUBLIC_KEY_PEM`) and `backend/docker-entrypoint.sh` writes them to
disk before the JVM starts, matching the file-path-based
`smallrye.jwt.sign.key.location` config the app already uses locally. See
`docs/runbooks/secrets-rotation.md`.

## Consequences

- Bringing your own domain (with a Route 53-delegated hosted zone) is a hard
  prerequisite for both environments, documented in the bootstrap runbook.
- Tearing down and recreating the AWS account boundary between staging and
  production later is possible but not free - budgets, IAM, and Terraform
  state would need to be split out.
- Rotating the JWT signing key (intentionally or via `terraform taint`)
  invalidates every outstanding guest token immediately, bouncing connected
  players to reconnect. Acceptable for a private, low-stakes game.
