# Runbook: rotating secrets

## Guest JWT signing keypair

The RS256 keypair used to sign/verify guest seat tokens is generated by
Terraform (`infra/modules/jwt-keys`) and stored in Secrets Manager as
`<project>/<environment>/jwt-private-key` and `.../jwt-public-key`. It is
delivered to the running task as environment variables and materialized to
disk by `backend/docker-entrypoint.sh` (see ADR 0005 for why files, not a
native secret mount).

**Rotating it invalidates every outstanding guest token immediately** -
every connected player is disconnected and must rejoin with a fresh invite
link. For a private, low-stakes game this is an acceptable (if disruptive)
cost; there is no dual-key grace period implemented.

To rotate:

```bash
cd infra/envs/<environment>
terraform taint module.jwt_keys.tls_private_key.jwt
terraform apply
```

This generates a new keypair, writes it to Secrets Manager, and (because
the task definition's `secrets` block references the same secret ARNs but
Terraform doesn't automatically restart running tasks on secret value
changes alone) you must force a new deployment to pick it up:

```bash
aws ecs update-service \
  --cluster $(terraform output -raw ecs_cluster_name) \
  --service $(terraform output -raw ecs_service_name) \
  --force-new-deployment
```

Do this during a low-traffic window and consider posting a heads-up if
anyone has a game in progress.

## AWS credentials

There are none to rotate. Every workflow authenticates via GitHub's OIDC
token exchanged for short-lived AWS credentials (`infra/bootstrap/iam.tf`);
nothing is ever stored as a long-lived AWS access key. If you ever suspect
the OIDC trust itself is compromised, re-run `infra/bootstrap` after
reviewing/tightening the `sub` claim conditions in `iam.tf`.

## ACM certificate

Fully managed by Terraform + Route 53 DNS validation
(`infra/modules/certificate`); it renews automatically as long as the
validation CNAME records remain in the hosted zone. No manual action
required unless the hosted zone itself moves.
